# 月面压力闭环 VLA Demo 架构重写草案

本文档是新架构的起点。当前分支有意从空白内容开始，目标不是修补旧
`lunar_maintenance_demo`，而是重新定义一个论文用真机 demo 的最小系统。

后续建议把本文拆成两个平行文档：

1. `ARCHITECTURE.md`：给人类阅读，解释系统目标、边界、运行拓扑和实验流程。
2. `AGENT_IMPLEMENTATION_GUIDE.md`：给 coding agent 使用，列出文件结构、接口契约、实现顺序和测试要求。

在拆分之前，本文同时保存这两类内容的草案和待确认模板。

## 1. 已确定目标

### 1.1 Demo 定位

- 这是论文用真机 demo，不追求通用产品化框架。
- 只支持一个压力表、一个阀门、一个目标管路。
- 不保留旧 repo 的 simulator、mock VLA、HTTP VLA、ROS stub、通用 CLI。
- 新 repo 应以 Python 脚本作为入口，不再以 `lunar-demo ...` CLI 作为主要操作方式。
- Gemini 只做视觉读表，不生成机器人动作，不做高层规划。
- 本地 deterministic planner 负责从压力误差生成阀门动作意图。
- OpenPI/VLA 只接收短时、固定 wording 的 canonical prompt。
- RoboCOIN 机器人侧尽量保持原工作方式：持续采集 observation，发送给 policy server，接收 action chunk 并执行。

### 1.2 明确不做

- 不做多阀门、多压力表、多管线扩展。
- 不做非压力任务的透明转发；非本任务直接跑 OpenPI server，不经过本 repo。
- 不接入独立电子压力传感器。压力来源是相机图像中的机械压力表读数。
- 不依赖 force/torque/jam/slip telemetry，因为真机当前拿不到这些信号。
- 不做 valve angle estimation 或机械限位视觉估计。
- 不在本 repo 中训练 VLA，不直接控制机器人关节。

## 2. 系统边界

### 2.1 LunarPressure 新 repo

负责：

- 运行 OpenPI-compatible orchestration server。
- 接收 RoboCOIN robot client 发来的 observation。
- 从 observation 中取出相机图像，调用 Gemini 读压力表。
- 校验 Gemini JSON、置信度和视觉读数。
- 计算目标压力与当前压力的误差。
- 生成 canonical OpenPI prompt。
- 在一个动作阶段内，多次把 canonical prompt 和最新 observation 转发给真实 OpenPI policy server。
- 记录每轮图像、Gemini 原始响应、解析结果、planner 决策、canonical prompt、OpenPI action chunk 和 timing。
- 提供最小 dashboard 或 replay API，用于查看最近一次实验。

不负责：

- 机器人 SDK 初始化。
- 机器人动作下发。
- OpenPI 模型训练。
- 非压力任务。

### 2.2 RoboCOIN

负责：

- 机器人连接、相机采集、关节状态读取。
- 按固定频率调用 policy server。
- 接收 `action` 或 `actions` chunk 并逐步执行。
- 后续需要加入一个最小 stop-control hook：当 LunarPressure server 返回停止控制信号时，机器人侧停止继续下发 VLA 动作，进入安全停机或保持姿态。

当前已知 observation 行为：

- `robot_client_openpi.py` 会发送 `prompt`，其值来自 `--task`。
- 它会构造 `observation.state`。
- 它还会构造 `observation.joint_position`、`observation.joint_velocity`、`observation.gripper_position`。
- 对所有 `observation.*` key，它会额外生成 slash 版本，例如 `observation.scene_image` -> `observation/scene_image`。
- 当前实际相机 key 倾向使用：
  - `observation.scene_image`
  - `observation.wrist_image`

### 2.3 openpi-lunarbot

负责：

- 运行真实 OpenPI policy server。
- 加载 RM75 fine-tuned checkpoint。
- 接收 canonical prompt 和 observation。
- 返回 action chunk。

当前 RM75 policy 侧支持的相关输入：

- `observation.scene_image` / `observation.wrist_image`
- `observation.images.scene_image` / `observation.images.wrist_image`
- `observation.state`
- split joint fields: `observation.joint_position`、`observation.joint_velocity`、`observation.gripper_position`
- `prompt`

待确认最终 inference contract 以哪组 key 为准，见第 8 节。

## 3. 运行拓扑

推荐真机运行形态：

```text
Robot PC / RM75 side
  RoboCOIN robot_client_openpi.py
    captures cameras + robot state
    sends obs to ws://<gpu-ip>:<lunar-port>
    receives action chunks or stop control
    executes robot actions

GPU workstation
  LunarPressure orchestration server
    speaks OpenPI websocket protocol to RoboCOIN
    calls Gemini API for gauge reading
    rewrites high-level task into canonical VLA prompt
    forwards canonical prompt to real OpenPI server

  openpi-lunarbot policy server
    serves fine-tuned RM75 OpenPI policy
    receives canonical prompt
    returns action chunks
```

Important principle: RoboCOIN keeps sending the original high-level `--task`, such as
`Keep Line-B pressure at 0.42 MPa`. LunarPressure owns the closed-loop state and
decides which canonical prompt is sent to OpenPI at each phase.

## 4. Closed-loop State Machine

The system should not treat one `infer()` call as a complete valve action. One
canonical VLA prompt may require multiple action chunks over a configured action
window before the robot has meaningfully completed the motion.

Proposed state machine:

### 4.1 `OBSERVE`

Input:

- Latest RoboCOIN observation.
- Scene/wrist images.
- Current high-level task.

Behavior:

1. Select image(s) for Gemini, preferably in-memory numpy arrays to reduce latency.
2. Call Gemini gauge-reading prompt.
3. Parse strict JSON into local `GaugeReading`.
4. Log raw Gemini response and parsed output.
5. If parsing fails or confidence is too low, stay in `OBSERVE` and retry on a newer frame.

Output:

- Valid visual pressure reading, or stop/retry decision.

### 4.2 `PLAN`

Input:

- Target pressure.
- Tolerance.
- Latest `GaugeReading`.

Behavior:

1. Compute pressure error: `target_pressure_mpa - current_pressure_mpa`.
2. If inside tolerance, transition to `STOP`.
3. If below target, choose the valve direction that increases pressure.
4. If above target, choose the valve direction that decreases pressure.
5. Choose action magnitude conservatively.

Output:

- A `LocalPlan`, not a model-generated plan.

### 4.3 `ACT`

Input:

- Canonical prompt selected by planner.
- Latest RoboCOIN observations from the websocket loop.

Behavior:

1. For a configured action window, forward each new observation to the real OpenPI server with the canonical prompt.
2. Return the OpenPI action chunk to RoboCOIN.
3. Save action chunks and timing metadata.
4. After the action window expires, transition back to `OBSERVE`.

This action window is a required design parameter. It can be expressed by duration,
number of policy calls, number of action chunks, or a combination.

### 4.4 `STOP`

Input:

- Target reached, unsafe condition, operator stop, or unrecoverable perception failure.

Behavior:

1. Return a stop control response to RoboCOIN.
2. RoboCOIN should not send the stop prompt to VLA as a normal manipulation prompt.
3. RoboCOIN should directly stop/hold/retreat according to the agreed stop protocol.

The exact stop protocol is not yet decided. See section 8.

## 5. Canonical VLA Prompts

Canonical prompts are fixed strings used both during data collection/training and
during inference. They reduce ambiguity and prevent Gemini or any LLM from
inventing robot actions.

Draft minimal label set:

```text
Turn valve V2 counterclockwise slightly.
Turn valve V2 clockwise slightly.
Turn valve V2 counterclockwise a tiny amount.
Turn valve V2 clockwise a tiny amount.
Stop and move the arm back to the observation pose.
```

Question to fill:

- Which exact strings were used or will be used in VLA data collection?
- Does `counterclockwise` increase or decrease pressure for the physical setup?
- Do we need both `tiny` and `slightly`, or only one magnitude for the paper demo?
- Should stop be represented as a canonical OpenPI prompt, a RoboCOIN control command, or both?

## 6. Observation Contract

### 6.1 Incoming RoboCOIN Observation

Expected keys:

```text
prompt
observation.scene_image
observation.wrist_image
observation.state
observation.joint_position
observation.joint_velocity
observation.gripper_position
observation/scene_image
observation/wrist_image
observation/state
observation/joint_position
observation/joint_velocity
observation/gripper_position
```

Only a subset is required by each component:

- Gemini gauge reader needs image arrays.
- OpenPI policy server needs image arrays, state/proprioception, and canonical `prompt`.
- Logger needs image snapshots, prompt, action chunks, and timing.

### 6.2 Internal Data Representation

Latency-sensitive path should prefer in-memory numpy arrays.

Do not write images to disk before calling Gemini or OpenPI unless a library
forces it. Logging can save images asynchronously or after the response is sent.

### 6.3 Forwarded OpenPI Observation

LunarPressure should forward the original observation with only `prompt` replaced
by the canonical prompt, unless we explicitly decide to normalize key names.

Open question:

- Should LunarPressure forward dot keys, slash keys, or both?
- Should LunarPressure resize/convert images, or rely on RoboCOIN/OpenPI policy transforms?

## 7. Safety Model

Safety here is paper-demo conservative logic, not a certified robot safety system.

Current safety sources:

- Gemini JSON schema validity.
- Gemini confidence.
- Visual pressure hard bounds.
- Max action window.
- Max number of observe/act cycles.
- Stop command path.
- Human/operator emergency stop outside this repo.

Not available:

- Independent pressure sensor.
- Force/torque telemetry.
- Jam/slip detection.
- Valve angle estimate.

Draft stop conditions:

- Gemini cannot return valid pressure after N retries.
- Gemini confidence remains below threshold.
- Visual pressure is outside hard min/max.
- Closed-loop max cycles reached.
- Target pressure reached.
- Operator stop requested.

## 10. Coding Agent Implementation Guide Draft

When implementation begins, coding agent should follow these constraints:

- Do not port old simulator code.
- Do not preserve old CLI.
- Do not keep generic VLA adapters unless needed by the real OpenPI path.
- Keep the main closed-loop logic in one orchestrator state machine.
- Keep Gemini as `GaugeReader`, not `Brain`.
- Keep planner deterministic and testable.
- Keep all task-specific constants in one config file.
- Optimize latency on the main path: avoid image disk roundtrips before Gemini/OpenPI calls.
- Make logging comprehensive but not blocking.
- Add tests only around contracts and deterministic logic at first.

Initial implementation phases:

1. Define schemas and config.
2. Define observation extraction contract from RoboCOIN observations.
3. Implement Gemini gauge reader with strict parsing and raw response logging.
4. Implement deterministic local planner and canonical prompt compiler.
5. Implement OpenPI-compatible websocket orchestrator server.
6. Implement OpenPI backend client wrapper.
7. Add stop-control response and document required RoboCOIN hook.
8. Add smoke scripts.
9. Add minimal dashboard/latest-run viewer.
